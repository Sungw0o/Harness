## 먼저 읽을 근거

1. 루트와 변경 영역(frontend/backend)의 `AGENTS.md`
2. MR diff 전체와 연결된 작업 키(LOCAL/Jira)의 범위·완료 조건
3. 변경이 계약에 닿는 경우에만 관련 Notion 요구사항·API 명세

## 점검 순서

1. diff가 작업 키의 목적 하나에 부합하는지, 무관한 변경이 섞였는지 확인한다.
2. 규칙 위반을 확인한다: 도메인 패키지 구조, Entity 직접 노출, 공통 응답 계약, 금지된 로그.
3. 계약 누락을 확인한다: API 변경인데 OpenAPI·계약 테스트 미수정, Schema 변경인데 Flyway migration 누락.
4. 테스트를 확인한다: 실패 경로·경계값 테스트 존재 여부, 커버리지 게이트 통과 여부, 의미 없는 숫자 채우기 테스트 여부.
5. 보안을 확인한다: Secret·개인정보, 입력 검증, 인증·인가 경계.
6. 성능·정합성을 확인한다: N+1, 트랜잭션 경계, 동시성, 외부 API 실패 처리.

## 완료 기준

- 지적마다 파일:라인과 blocking / non-blocking 구분이 있다.
- 칭찬이나 요약이 아닌 실행 가능한 지적만 남긴다.
- 확신이 없는 항목은 단정하지 않고 질문 형태로 구분해 표시한다.

## 금지·승인

- 리뷰 중 코드를 직접 수정하지 않는다. 수정은 작업자가 한다.
- diff에서 Secret이 발견되면 리뷰를 중단하고 즉시 보고한다.
- PR-Agent 도입 시 이 점검 순서를 `.pr_agent.toml` 프롬프트의 원본으로 사용한다.
